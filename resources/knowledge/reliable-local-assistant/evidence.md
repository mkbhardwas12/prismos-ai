# Evidence provenance and avoiding self-reinforcing mistakes

Reviewed: 2026-09-08. Classification: public reference; original engineering guidance.

Useful provenance includes source location, author or publisher, capture date, content date where known, content hash, extraction method, and whether the material is user supplied, vendor published, model generated, or manually verified. A record's access count, rating or embedding similarity is not factual confidence.

Keep four distinctions visible: supplied requirement, independently supported fact, tentative inference, and unknown. Cite only a source that was actually available and supports the nearby claim. When sources conflict, report the conflict and its consequences instead of averaging incompatible statements. Version-sensitive technical instructions need evidence applicable to the actual installed product and configuration.

Never promote an assistant's old answer to trusted evidence merely because it was stored or repeated. Positive feedback may indicate helpfulness, tone or formatting; it does not certify technical accuracy. Generated summaries should point back to original sources. Source retirement should remove material from answer retrieval while preserving an audit trail where needed.

A verification checklist asks: which source supports this claim, does it concern the right version and environment, is it current enough, does another reliable source disagree, and what action would be unsafe if it were wrong? If support is absent, label the claim unverified or omit it.
